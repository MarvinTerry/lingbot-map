# lingbot_map_server 可行性与开发方案

## 1. 需求理解

你计划新增 `lingbot_map_server/`，目标大致是：

- 接收 `mp4`
- 运行 LingBot-Map 推理
- 输出 `GLB`
- 或输出第一人称飞行视频
- 或持续循环推流第一人称视频

这个方向是可行的，但建议明确优先级，不要一开始就把“上传、推理、渲染、推流、实时交互”一次做全。

## 2. 可行性判断

### `mp4 -> GLB`

完全可行，而且是最稳的一条线。

- 仓库已有 `--video_path` 推理入口。
- 仓库已有 `predictions_to_glb()`。
- 服务端只需要补上传、任务管理、产物存储、状态查询。

### `mp4 -> 第一人称 mp4`

可行，难度中等。

- 当前 viewer 已具备相机跟随和视频导出基础。
- 还需要补自动镜头规划和批处理导出链路。
- 重点不在“能不能做”，而在“如何让镜头更顺、更好看”。

### `mp4 -> 循环推流第一人称视频`

可行，但不建议作为第一阶段核心目标。

- 如果只是把已经渲染好的 `mp4` 循环播出去，技术上很直接。
- 如果你想做“任务一完成就自动上线播放”的伪直播，也不难。
- 真正难的是低延迟、多人观看、断线恢复、播放器兼容、带宽控制。

结论：

- 批处理 `GLB`
- 批处理第一人称 `mp4`
- 已生成视频的循环推流

这三件事都可行，但工程优先级应该是递增的。

## 3. 我的专业建议

最值得先做的不是“实时建图服务”，而是“异步批处理服务”。

原因：

- LingBot-Map 推理本身就是 GPU 重任务，不适合先追求同步 HTTP 处理。
- 第一人称视频本质也是离线渲染任务。
- 真直播链路会把复杂度从模型问题扩展到媒体服务问题。

建议先把产品定义成：

“上传一个视频，异步生成三维点云结果和一个可传播的飞行视频。”

这个定义更稳，也更容易尽快做出可交付版本。

## 4. 推荐的分阶段路线

### Phase 1：批处理建图服务

目标：

- 上传 `mp4`
- 创建 job
- 抽帧
- 推理
- 导出 `glb`
- 查询状态
- 下载结果

建议接口：

- `POST /jobs`
- `GET /jobs/{job_id}`
- `GET /jobs/{job_id}/artifacts`
- `GET /artifacts/{artifact_id}`

建议产物：

- `scene.glb`
- `metadata.json`
- `log.txt`
- 可选 `preview.jpg`

这是第一优先级，投入产出比最高。

### Phase 2：第一人称视频导出

目标：

- 在建图完成后，自动生成一版第一人称飞行视频。

建议补的能力：

- 从重建相机轨迹生成平滑相机路径
- 控制速度、视角、抬头方向、前视偏移
- 导出 `camera_path.json`
- 输出 `flythrough.mp4`

建议先追求：

- 稳定
- 可复现
- 参数少但有效

不建议一开始就做非常复杂的镜头语言系统。

### Phase 3：循环推流

目标：

- 把 `flythrough.mp4` 持续输出为一个可观看的视频流。

推荐方式：

- 内网或工程调试优先：`RTSP`
- 浏览器兼容优先：`HLS`
- 低延迟强交互优先：`WebRTC`

如果只是“循环播放一个已经生成的视频”，最低成本方案通常是 `ffmpeg` 做循环推流。

## 5. 推荐的目录设计

建议未来新增：

```text
lingbot_map_server/
├── __init__.py
├── api/
├── core/
├── jobs/
├── render/
├── storage/
├── workers/
└── schemas/
```

职责建议如下：

- `api/`
  - FastAPI 路由与 HTTP 接口。
- `core/`
  - 配置、路径规则、公共常量、日志。
- `jobs/`
  - job 生命周期、状态机、任务编排。
- `render/`
  - `GLB` 导出、相机路径平滑、第一人称视频生成。
- `storage/`
  - 本地文件布局、对象存储抽象、artifact 管理。
- `workers/`
  - 真正执行抽帧、推理、渲染的 GPU worker。
- `schemas/`
  - Pydantic 请求/响应模型。

## 6. 推荐的最小实现架构

如果你现在只有一台 GPU 机器，最小可行架构可以非常克制：

- `FastAPI` 负责接收上传和查询状态
- 一个本地 job 队列负责串行或限并发执行
- 推理和渲染直接调用仓库现有 Python 逻辑
- 所有产物都写入 `outputs/jobs/{job_id}/`

这比一上来拆成很多服务更适合当前阶段。

建议 job 目录长这样：

```text
outputs/jobs/{job_id}/
├── input/
├── frames/
├── predictions/
├── render/
├── artifacts/
├── logs/
└── metadata.json
```

## 7. 技术选型建议

### API 层

- 推荐：`FastAPI`
- 原因：类型清晰，异步接口友好，和 `uv` / Python 工具链兼容好。

### 任务执行

- 第一版推荐：进程内 job 队列或单机 worker
- 第二版再考虑：Redis + RQ / Celery / Dramatiq

如果当前重点是尽快做出服务，先不要把消息队列系统引进来。

### 视频处理

- 推荐：`ffmpeg`
- 用途：抽帧、拼视频、转码、循环推流

### 渲染策略

- 第一版推荐：复用现有 viewer 视角导出逻辑，或补一个离线相机路径渲染器
- 中期可选：Blender 离线增强
- 长期可选：surfel / splat 渲染

## 8. 风险与难点

真正的难点不是上传接口，而是下面这些：

- GPU 资源调度
- 长视频推理耗时
- 大量帧的磁盘占用
- 第一人称镜头的平滑与观感
- 点云近景穿越时的视觉缺陷
- 推流链路的稳定性与协议选型

其中我最建议优先处理的是：

1. job 目录规范
2. 任务状态管理
3. 第一人称镜头平滑

## 9. 结论

这个方向值得做，而且能做成。

但最务实的落地顺序应该是：

1. 先做异步批处理服务
2. 稳定产出 `GLB`
3. 再稳定产出第一人称 `mp4`
4. 最后再做循环推流

如果现在就把目标定成“上传视频后自动返回 `GLB + 飞行视频`”，我认为这是一个非常合理、工程风险可控、展示效果也足够强的版本定义。
